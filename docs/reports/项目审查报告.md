## 1. 项目概览

DocFlow 是一个基于 Electron + React + TypeScript 的多引擎文档批量处理桌面工具。核心功能是将 PDF、Office 文档、图片等格式的文件提交到 MinerU Cloud、PaddleOCR Cloud 或本地 PaddleOCR 服务进行智能识别和结构化输出。

### 1.1 技术栈

| 层级 | 技术 | 用途 |
|------|------|------|
| 桌面框架 | Electron 28 | 跨平台桌面壳 |
| 前端框架 | React 18 + TypeScript | UI 渲染 |
| 构建工具 | Vite 5 + vite-plugin-electron | 开发/构建 |
| 样式方案 | Tailwind CSS 3 + 自定义 CSS 变量 | 主题化样式 |
| 后端运行环境 | Node.js (Electron 主进程) | 文件处理、IPC |
| HTTP 客户端 | axios | API 调用 |
| 文档处理 | pdf-lib | PDF 页数统计 |
| 图像处理 | sharp | 图片分析 |
| 压缩处理 | adm-zip | ZIP 解压 |
| Python 桥接 | child_process (python-bridge) | 本地 OCR 服务 |

### 1.2 项目规模

| 类别 | 数量 |
|------|------|
| TypeScript 源文件（前端） | 21 个 |
| TypeScript 源文件（后端） | 18 个 |
| Python 脚本 | 1 个 |
| CSS 文件 | 1 个 (~39KB) |
| 总代码行数（近似） | ~6,500 行 |

## 3. 核心功能模块分析

### 3.1 文件处理流水线 (Pipeline)

```
scanner.ts ─── 扫描输入路径，过滤支持的文件格式
  ↓
preprocessor.ts ─── 分析文件元信息（类型、大小、页数、SHA-256）
  ↓
splitter.ts ─── 对超大文件按页数阈值拆分为多个 Chunk
  ↓
provider-router.ts ─── 根据优先级和健康状态选择 Provider
  ↓
[Provider Processing] ─── submit → poll → download
  ↓
merger.ts ─── 合并 Chunk 结果，收集图片，重写图片路径
  ↓
validator.ts ─── 验证输出完整性和格式规范
  ↓
output-normalizer.ts ─── 规范化文件名和目录结构
```

### 3.2 Provider 系统

| Provider | 类型 | Token | 日配额 | 支持格式 | 输出格式 |
|----------|------|-------|--------|----------|----------|
| MinerU Cloud | `mineru-cloud` | 需要 | 1000 页/天 | PDF, PPTX, DOCX, XLSX, Image | MD, JSON, HTML, DOCX |
| PaddleOCR Cloud | `paddleocr-cloud` | 需要 | 20000 页/天 | PDF, PPTX, DOC, DOCX, TXT, WPS, OFD, Image | MD, JSON |
| PaddleOCR Local | `paddleocr-local` | 无需 | 无限制 | PDF, Image | MD, JSON |

**故障转移机制**: 当当前 Provider 连续失败 2 次且无成功的 Chunk 时，自动切换到优先级列表中的下一个 Provider。

### 3.3 任务队列引擎 (TaskWorker)

- 并发控制: 1-8 个并发任务
- 状态机: pending → preprocessing → uploading → running → downloading → merging → done
- 暂停/恢复: 支持队列级别的暂停恢复
- 重试: 支持单个任务和批量失败任务的 Chunk 级重试
- 持久化: 通过 state-manager 定期保存任务状态到 JSON 文件

### 3.4 前端组件树

```
App
├── TopBar (导航: 任务列表 / 日志 / 设置)
├── Sidebar (侧栏操作)
│   ├── 添加文件 / 添加文件夹
│   ├── 全部开始 / 暂停恢复
│   ├── 清除已完成 / 重试失败
│   ├── 筛选: 全部 / 运行中 / 已完成 / 失败
│   ├── Provider 状态卡片
│   └── 任务统计 (累计/今日)
├── Main Content
│   ├── TaskList → TaskCard → ChunkPill
│   ├── LogsView (搜索+级别过滤)
│   └── SettingsView
│       ├── ProviderSettings (服务商配置+优先级拖拽+测试连接)
│       ├── GeneralSettings (基本设置)
│       ├── LocalInferenceSettings (本地推理)
│       └── AboutView (关于) ← 新增
├── StatusBar (底部状态栏: 进度+计数)
└── DragOverlay (拖放覆盖层)
```

### 3.5 设置管理

- **持久化**: 通过 `electron-store` 模式保存到 `docflow_settings.json`
- **兜底机制**: 所有文件 I/O 包装了 try-catch；AppData 不可写时回退到 `Documents/DocFlow_Data` 或 Temp 目录
- **默认设置**: 硬编码在 `state-manager.ts` 中，加载时合并已保存的值

### 6.2 ⚠️ 已知问题 / 边界情况

1. **沙箱环境文件 I/O**: 在 Codex 沙箱中 Electron 无权写入 AppData，已通过 try-catch + 回退路径修复，但在某些极端环境下可能仍需手动创建目录。

2. **Provider 配额硬编码**: MinerU Cloud 的 1000 页/天和 PaddleOCR Cloud 的 20000 页/天是硬编码在 `types.ts` 的 `PROVIDER_LIMITS` 中。实际 API 可能返回不同的限制值，建议未来通过 API 动态获取。

3. **Python 桥接**: `python-bridge.ts` 通过 `child_process` 管理 Python 子进程。本地 OCR 需要用户事先安装 Python 和 PaddleOCR 依赖。

4. **大文件处理**: 单个 Chunk 最大 200 页 (MinerU) / 100 页 (PaddleOCR)，超大文件拆分后并发处理，但 Chunk 合并时依赖原始顺序。

5. **图片渲染**: 文档中的图片由 Provider 返回后本地化存储，路径重写依赖于 Markdown 中的相对路径规范。如果 Provider 返回格式异常，可能导致图片无法显示。

6. **网络依赖**: MinerU Cloud 和 PaddleOCR Cloud 完全依赖网络连接，无离线模式。

7. **任务持久化**: 任务状态保存在 JSON 文件中，并发写入时可能导致数据覆盖。当前通过 task-worker 的 `emitUpdate` 在每次状态变更后同步写入。

### 6.3 🔴 待改进项

1. **Provider 配额动态查询**: 应从 API 实时获取配额而非硬编码。
2. **多语言支持**: 当前仅支持中文界面，国际化(i18n)未实现。
3. **单元测试**: 项目中无任何测试文件（jest/vitest）。
4. **打包发布**: electron-builder 配置存在但未验证打包产物。
5. **自动更新**: 无 Electron auto-updater 集成。
6. **错误上报**: 无 Sentry 或类似错误追踪。
